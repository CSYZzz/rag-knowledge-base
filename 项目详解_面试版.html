一、一句话说清它是什么

一个能读你自己的文档、并且回答时标明出处出自哪一段的问答系统。
你和 ChatGPT 的区别在于：ChatGPT 不知道你的文档，只能靠猜；这个系统把文档里相关的几段找出来，只让模型读这几段再回答，所以不会瞎编，而且每句话后面都有【资料N】标注来源。

技术上是 RAG（Retrieval-Augmented Generation，检索增强生成）：先检索，再生成。这两个词就是整个项目的骨架，其余全是细节。

二、为什么需要它

大模型有三个硬限制：

  1. 不知道私有数据。它没读过你们公司的产品手册、内部规章、技术文档。
  2. 会瞎编。不知道答案时，它倾向于编一个听起来合理的答案，而且语气一样自信。
  3. 上下文装不下整本书。就算把整份文档塞进去，模型对长文本中间部分的注意力会衰减，效果反而不如只给它相关的几段。

RAG 的解法很直接：每次只把最相关的几段喂给模型，让它基于这几段回答，并要求它标出来源。这样既解决了知识问题，又因为"有据可查"大幅降低了瞎编的概率。

三、整体架构

整个系统分两个阶段，只在第一次导入文档时执行前者。

【建库阶段 · 离线，只做一次】

  文档(txt/md/pdf)
        │
        ▼
  结构化分块 ──→ 按标题切节 → 节内段落打包 → 每块加【章节名】前缀
        │
        ├──→ BGE 向量化（512 维）──→ 存 vectors.npy
        │
        └──→ 分词建 BM25 索引（中文 2-gram）

【查询阶段 · 在线，每次提问都走】

  用户问题
        │
        ├──→ 向量检索（余弦相似度）──┐  各取 Top-10
        └──→ BM25 关键词检索 ───────┘
                                     │
                                     ▼
                              RRF 融合（排名倒数相加）
                                     │
                                     ▼
                              LLM 重排（看全文重新排序）
                                     │
                                     ▼  取前 4 块
                          拼 Prompt + 注入 4 块资料
                                     │
                                     ▼
                          DeepSeek 流式生成 + 【资料N】引用

四、建库阶段：三个决定效果的选择

1. 分块（chunking）—— 影响最大的环节

问题：文档动辄几千字，不能整篇塞进模型。必须切成小块，每块单独打索引。但怎么切，直接决定效果。

最朴素的做法是按固定字数切（比如每 400 字一刀）。我一开始就是这么做的，结果发现两个毛病：

  • 句子被劈开。「同时确认测温探头…」被切成两块，后一块开头是「时确认测温探头」，成了残句，单独拿出来读不通。
  • 跨章节。一块里可能前半是「安装说明」、后半是「操作说明」，语义混杂，检索时对哪个问题都不够像。

我改成按文档结构切：

  1. 先按标题（一、二、 / ## / 第一章）切成大节，保证一块绝不跨节
  2. 节内按段落（或单行）打包，尽量装满但不超过 400 字
  3. 只有单个段落自己就超长，才退回滑动窗口
  4. 每块前面注入「【章节名】」——这样块脱离上下文也能读懂，检索时章节名也参与匹配
效果：Top1 命中率从 43.5% 提升到 69.6%。
块数从 6 变成 8，跨节 0 次，残句 0 个，块间重复从 100% 降到 0。

2. 向量化用什么模型

用 BAAI/bge-small-zh-v1.5，512 维，约 95MB。选它的理由：中文专用、体积小、CPU 上跑得动、本地不花钱、数据不出本机。

另外有个官方要求的细节：检索时问题要加一个前缀「为这个句子生成表示以用于检索相关文章：」，效果明显更好。这是因为 BGE 训练时对查询和文档用了不同的处理方式，不加前缀等于用错了姿势。

3. 向量存哪

没有用 chromadb / FAISS，自己写了一百多行：向量存 vectors.npy，文本和元数据存 meta.json。

原因有两个，一个被动一个主动：

  • 被动：chromadb 在项目的运行环境里装不上。
  • 主动：数据只有几百到几千块时，暴力算余弦相似度比建索引还快，而且实现完全透明。向量先做 L2 归一化，余弦相似度就等价于点积，一次矩阵乘法 vectors @ q 就能算出全部得分，排序取前 k。

什么时候该换回专业向量库？数据量到十万级以上，暴力计算撑不住，那时才需要 HNSW 之类的近似最近邻索引。知道边界在哪，比知道怎么用更重要。

五、查询阶段：为什么这么绕

如果只做"问题 → 向量检索 → 喂给模型"，代码只有三十行。但这个版本经不起细问，因为召回和排序都会出错。下面每一步都是为了补一个具体的漏洞。

第一步：双路召回，为什么要两路

向量检索擅长"意思相近"，弱在"字面精确"。实测有个典型例子：

问「设备能装在室外吗」，向量检索把【八、维护建议】排在第一，因为那里有「恒温环境」——语义上跟"室外"最近。但真正的答案在【三、安装说明】：「设备应安装在通风良好、避免阳光直射的位置」。

而 BM25（关键词检索）恰好相反：它算的是词的重要性，「设备」「装」这两个词在【三、安装说明】里密集出现，在【八、维护建议】里几乎没有，所以 BM25 能给这块很高的分数。

两路一合并，正确答案就被顶上来了。Top1 从 69.6% 到 78.3%。
BM25 的实现细节：中文没有天然的词边界，我没引入 jieba 这类分词库，而是用字符 2-gram（连续两个字算一个词），配合 IDF 加权。对中文短查询这个粒度够用，且零依赖。

第二步：RRF 融合，为什么不用加权求和

两路的分数根本不是一个尺度：向量那边是余弦相似度（0~2），BM25 那边可能是十几。直接相加，等于让 BM25 单方面说了算。

RRF（Reciprocal Rank Fusion）的做法是只看排名，不看分数：

score(文档) = Σ  1 / (k + 它在第 i 路里的名次)      k = 60

例：某块在向量里排第 2、BM25 里排第 5
    → 1/(60+2) + 1/(60+5) = 0.0161 + 0.0154 = 0.0315

好处是天然跨尺度、不需要调权重。k=60 是原论文的经验值，作用是让头部排名之间的差距不那么剧烈。

第三步：重排，为什么必须要

不加重的检索结果是 78.3%。剩下的错误有个共同特征：10 题里 9 题是「正确答案排第 2 名」，只有 1 题是真的没召回到。

这说明问题不在"找不到"，而在"差一名"。而"差一名"这件事，换更好的 embedding 是治不好的——模型已经尽力了。要治它得用不同结构的模型。

bi-encoder（我们的检索模型）
  问题 ──→ 向量 ┐
                 ├─→ 算相似度
  文档 ──→ 向量 ┘
  优点：文档可预先编码，检索快
  缺点：问题和文档从没见过面

cross-encoder（重排模型）
  [问题 + 文档] ──→ 一起送进模型 ──→ 一个相关性分数
  优点：能看到两者的词与词之间的关系，精度高得多
  缺点：每对都要跑一次，慢，只能用在少量候选上

所以是两阶段：先用便宜的 bi-encoder 从全库粗筛 10 条，再用贵的 cross-encoder 精排这 10 条。这也是工业界做检索的标准架构。

我这里没有用 cross-encoder 模型，而是用 LLM 做重排。原因是 bge-reranker-base 基于 xlm-roberta，权重 1.1GB，在当前网络环境下拉不下来。LLM 重排原理相同（把候选和问题一起交给模型判断），代价是多一次 API 调用、多 1~3 秒。代码里保留了三种后端可切换。

加上重排后：Top1 到 97.8%，Recall@4 到 100%，平均命中名次 1.02。

第四步：生成阶段的约束

Prompt 里写了三条硬规则，这是防瞎编的关键：

  1. 只能依据资料回答，资料里没有就直接说「资料中未提及」，不要编。
  2. 必须用【资料N】标注引用来来源。
  3. 回答简洁，不要复述原文。

温度设为 0.2，偏低，减少随机性。注意：这里不用 temperature=0，因为完全确定性有时会让回答过于僵硬。

六、实测数据

评测方法：自建 50 题（事实查询 38 / 多跳推理 4 / 文档无答案 4），每题标注答案关键词。只看"检索到的块里有没有答案"，不看模型生成得漂不漂亮——因为生成质量主观，检索命中是客观的。

配置Top1 命中Recall@4平均名次
朴素分块 + 纯向量 20/46 = 43.5% 97.8% 4.09
结构化分块 + 纯向量 32/46 = 69.6% 97.8% 3.61
结构化分块 + 混合检索 36/46 = 78.3% 97.8% 3.35
+ 重排 45/46 = 97.8% 100% 1.02
这个 97.8% 有明确的前提，说的时候必须带上：单文档、8 个块、10 个候选的小规模知识库。
真实企业场景候选是几百上千条，噪声大得多。小规模下重排能把排序问题基本清干净；规模上去后，瓶颈会转移到召回——候选里压根没有正确块，重排也救不回来。那时候该做子块拆分和索引优化，而不是继续加重排。

七、三个坑（这段最能体现真实做过）

坑一：向量库装不上，于是自己写

chromadb 在 Python 3.13 上装不上，报 No matching distribution found。查下来是下载源的问题，不是版本问题——换源后确认了这一点。

最后决定不折腾环境，自己用 numpy 实现向量存储与检索，接口与上层解耦。这个决定是对的：几百条数据下暴力检索更快，而且面试时能讲清每一行在干什么。

坑二：重排让指标反而下降

第一版重排上线后，Recall@4 从 97.8% 掉到 91.3%，平均名次从 3.35 恶化到 9.87。原因是候选块在送进模型前被我截断到前 100 字。

而答案大量位于块的中后部：

  • 「现象四：继电器频繁动作」在 300 字之后
  • 「120 欧姆终端电阻」约在 150 字处
  • 「长按 SET 键 3 秒」在块中段

模型看不到答案，自然把这些块排到后面，正确答案就被挤出了前四。为了省 token 而截断，省下的代价是丢掉答案。

坑三：让重排模型「只挑 Top-4」是个设计错误

原来的提示词是"只输出最相关的 4 个编号"。这等于让它承担过滤职责——一旦判断失误，正确答案直接被丢弃，无法挽回。

改成"输出全部 10 个候选的完整排序"后，最坏情况只是顺序错，答案仍在候选里。

结论：重排器只该排序，不该过滤。过滤是召回阶段的职责。

八、面试 15 问

1. 为什么不用 LangChain / LlamaIndex 现成的？
因为我需要说清每一层在干什么。框架把这些都封装好了，用它我能很快搭起来，但被问到"RRF 为什么用排名倒数而不是加权"时我答不出细节。这个项目每个模块都是我手写的，包括分词、BM25、RRF、向量检索——好处是任何一层出问题我都能定位。当然，生产环境我会优先用成熟框架，手写只是学习阶段的选择。
2. 分块大小怎么定的？为什么是 400 字？
400 字是个折中：太小则单块信息不完整，检索到也用不上；太大则一个块混多个主题，向量被稀释，反而不好匹配。我实测过——有一块 323 字装了四个故障现象，问"地址范围"时这块没能进前四，就是被稀释了。更好的做法是父块/子块（parent-child）：用小块做检索，命中后返回它所属的大块给模型。这是我下一步要改的地方。
3. 为什么用 BGE，不用 OpenAI 的 embedding？
三个原因：本地跑不花钱、数据不出本机、中文效果好。OpenAI 的 embedding 要联网且按量计费，对这个场景不划算。但如果是多语言或者需要更强语义，我会考虑换。
4. 为什么自己写向量库，不用 FAISS？
数据量只有几百块，暴力算余弦相似度是微秒级，比建索引还快，而且实现完全透明——向量归一化后点积就是余弦相似度，一次矩阵乘法出全部得分。FAISS 的优势在百万级数据，我这里用不上。如果数据到十万级，我会换 HNSW 类索引。
5. RRF 的 k=60 是怎么来的？
原论文的经验值。它的作用是平滑头部排名——k 越小，第 1 名和第 2 名的分差越大；k 越大，差距越平缓。60 是论文里在多个数据集上表现稳定的默认值，我没有针对自己的数据重新调。
6. 为什么不直接让 LLM 读所有块，或者直接用 LLM 做检索？
成本和时间。文档大了以后，每次提问都把全文送进模型，token 消耗和延迟都不可接受。而且长文本中间部分的注意力会衰减，效果反而下降。检索的意义就是用便宜的方式先缩小范围。
7. 97.8% 是不是过拟合了你的测试集？
有这个风险，我必须承认。50 道题是我自己标注的，而我又看过失败样本去调优，客观上存在信息泄漏。更严谨的做法是留出一部分题只在最后测一次，或者用别人标注的题集。另外这个数字的前提是单文档 8 块的小规模库，不能外推到真实规模。
8. 怎么保证模型不瞎编？
三层：提示词约束（只能依据资料、没有就说未提及）、要求标注【资料N】来源、temperature 设 0.2 降低随机性。实测里有一道"设备能装在室外吗"，模型回答的是"资料中未提及设备能否安装在室外，仅提到应安装在通风良好、避免阳光直射的位置"——它没有替用户做推理判断，只陈述了文档里的事实，这个行为是我想要的。
9. 如果文档有一千份，你的方案哪里会先崩？
两个地方。第一是向量检索的暴力计算，一千份文档按每份 20 块算是两万块，逐次矩阵乘还能撑但会变慢，需要上索引。第二是重排——候选池从 8 个变成几万个，必须靠粗筛把候选压到几十条以内，重排才有意义。优先级是：先换索引结构，再调粗筛的候选数。
10. 表格和图片怎么处理？
目前不支持，这是明确的局限。表格如果按纯文本切会丢掉行列对应关系，正确做法是转成 Markdown 表格或结构化后再分块；图片需要 OCR 或视觉模型描述。当前的代码遇到扫描版 PDF 会读不出内容，我选择直接跳过而不是硬啃 OCR——先把主流程做对，再扩展到复杂格式。
11. 整个链路延迟多少？哪一步最慢？
最慢的是 LLM 重排和生成，各 1~3 秒；向量编码在 CPU 上几十毫秒；BM25 和 RRF 是毫秒级。所以如果要优化延迟，第一步是把重排换成小模型或者加缓存，而不是优化检索。这也解释了为什么生产上更倾向用本地 cross-encoder 而不是 LLM 重排。
12. 你怎么知道效果变好了？靠感觉吗？
不靠感觉，靠评测集。50 题标注了答案关键词，只看"检索到的块里有没有答案"，不看生成文本。这样快、免费、可重复，才能一次跑四组配置做消融。这个方法的出发点是：我早期发现过一题答案对、但检索其实是错的——模型靠 4 块里的第 2 名蒙对了。所以"回答对"不能作为唯一指标。
13. 你这个和 Dify / Coze 有什么区别？
Dify 能十分钟搭出同样的功能，而且更稳。区别在于我能讲清每一层的取舍——比如为什么 RRF 比加权求和合适、重排为什么要两阶段、分块粒度怎么影响召回。用 Dify 我也会用，但那是部署工具，不是理解。
14. 如果重新做一遍，你会改什么？
三件事。第一，父块/子块分块——小块检索、大块喂模型，能同时解决"块内主题太杂"和"上下文不足"。第二，加一套更严格的评测流程，评测集留出验证集，避免我自己调优带来的信息泄漏。第三，把重排换成本地 cross-encoder，延迟和成本都更可控。
15. 这个项目你花了多久？最难的是什么？
核心链路两天。最难的不是写代码，是判断"哪里出了问题"——比如重排上线后指标反降，如果只看总分我会以为是模型不行，实际上是输入被截断了。定位这个问题靠的是看失败明细、逐题核对答案在块里的位置。这件事让我意识到，做这类系统，可观测性比算法更重要。
